## 0. 한 줄

**아카이브를 새 저장소에서 다시 짓는다.** 겉은 무채색 장부 스타일로 덜어 내고(보기는 나무위키의 짜임, 편집은 작업대), 속은 HistoryTime과 같은 **Rust 엔진 한 벌**에 서재를 올린다. 아카이브 · HistoryTime · 히스토리챗은 **각자 따로인 앱이 서재 하나를 공유**하고, 서재에 쓰는 앱은 아카이브 하나다. 폰과 PC는 구글 드라이브를 운반로로 맞춘다.

## 1. 왜

감독의 말: "지금은 너무 슬롭같아." 셋 다 문제였다(물음 1).

- **겉모습** — 개성 없는 회색 목록 · 실선 상자 · 파란 링크, 빈 대문.
- **쓰는 느낌** — 기능(메뉴 막대 · 팔레트 · 우클릭 · 미리보기)은 붙었지만 읽고 쓰는 흐름이 손에 붙지 않는다.
- **속** — 패키지 11개, 앱에서 뺀 모듈 셋, 옮겨 심은 연표 6만 줄과 3-방향 합치기 도구, 쌓인 설계 · 보고 문서.

제품의 정체(개인 역사 서재 위키 + 자전)는 그대로 둔다. 감독이 가장 공들일 장면으로 고른 것: **폰과 PC가 이어지고, 위키 문서를 만들고, 링크 · 각주 · 분류를 달아 서재를 키우고, 연표 앱과 문서를 자유자재로 주고받는 생태계**, 그리고 **한자 찾기(자전)**.

## 3. 디자인

목업이 기준이다(`design/remake/`). 아래는 목업에서 굳힌 규칙이다.

### 3-1. 스타일 — 무채색 장부

taste-skill이 이 앱에 내준 스타일(`design/remake/taste-skill-direction.json`, achromatic-ledger · seed 1468870555)을 따른다. 틀(chrome)에는 색이 없다.

| 토큰 | 값 |
| --- | --- |
| 바탕(얼굴) | 돌빛 `#f4f3f1` — 그 위에 흰 문서 종이 `#ffffff` |
| 한 단계 바탕 · 지금 위치 | `#f6f5f3` · `#e7e6e3`(중립 회색 칠, 왼쪽 강조선 없음) |
| 선 | 상자 `#e4e3e0` · 줄 `#efeeec` · 입력 `#d4d3d0` |
| 글자 | 먹 `#0a0a0a` · 둘째 `#3d3d3d` · 셋째 `#6b6b6b`(흰 바탕 · 돌빛 바탕 모두 4.5:1 이상) |
| 모서리 | 종이 6 · 단추 5 · 칩 4 |
| 그래프 한 색(주홍) | `#fbeee9` `#f3c9bd` `#e58c74` `#cf4f35` `#8f2a1b` — **그래프 안에만** |
| 그림자 | 떠 있는 것(자전 카드 · 잇기 목록)만, 8% 아래 |

- 진한 검정 칠 · 실선 단추를 쓰지 않는다. 주 동작(편집 · 저장 · 새 문서)은 옅은 회색 칠, 나머지는 글자 단추.
- 링크는 먹 글자에 옅은 밑줄, 없는 문서는 흐린 점선.
- 위쪽 막대 없이 사이드바가 바탕 위에 놓인다(Open plane). 폰은 48px 위 막대(≡ · 제목 · 字 · 주 동작)로 접는다.

### 3-2. 글자

- 프리텐다드 한 벌(Geist 대신 — Geist에는 한글이 없다). 쓰는 무게 400 · 600 · 700. 제목은 앱 화면 규칙대로 24~32px.
- 한자는 명조: Noto Serif KR(KS X 1001) → 花園明朝 A → B. 프리텐다드에는 한자가 0자라 한자에는 명조가 반드시 필요하다.
- 원문 편집기는 D2Coding. 글꼴 세 벌은 역할이 하나씩이다(taste-skill의 '두 벌까지' 경고는 이 까닭으로 받아들인다).

### 3-3. 얼굴

- 돌빛 바탕 위의 흰 문서 종이, 명조로 짠 한자(제목 옆 원어 · 자전 카드), '펼친 기록' 심벌(`design/brand/archive-mark.svg`의 두 장 종이, 바탕 네모 없이).

### 4-2. 자료의 주인

| 자료 | 주인 · 쓰는 앱 | 동기화 |
| --- | --- | --- |
| 서재(문서 · 판 · 첨부) | 아카이브만 쓴다. 기기마다 한 벌 | 구글 드라이브(6절) |
| 자전(《康熙字典》) | 아카이브가 싣는 참고 자료, 읽기 전용 | 안 함 |

### 4-3. 흐름 — HistoryTime에서 사건을 누르면

1. HistoryTime이 서재 창구에 `docs_for_entity(항목ID)`를 묻는다.
2. 받은 그리기 모델을 `library_view`로 전문 그린다.
3. 「고치기」 → `historyarchive://edit/<문서ID>`로 아카이브의 편집 화면이 열린다.
4. 저장하면 아카이브 엔진이 판을 더하고 색인을 고치고, 바뀐 내역 묶음을 드라이브로 올린다.

### 4-4. 첫 판에 드는 것

HistoryCore의 서재 엔진, 아카이브 앱, 동기화, 서재 창구. HistoryTime과 맞물리는 약속은 `spec/`에 먼저 정하고 HistoryTime 쪽 구현은 그 저장소의 일정에 맞춘다. 챗은 다음 판.

## 5. 서재 형식

### 5-1. 문서의 정체

- 문서마다 **바뀌지 않는 ID**(UUIDv7). 판 · 동기화 · 연표 연결 · 창구 질의는 모두 ID로 한다.
- 본문 링크 `[[제목]]`은 제목으로 쓰고 색인이 ID로 푼다. 제목을 바꾸면 옛 제목에 넘겨주기를 남길지 고른다(기본: 남김).
- 이름공간: 문서 · 분류 · 틀 · 파일 · 대문. 字(자전)와 연표는 서재 밖 자료를 가리키는 이름공간이다.

### 5-2. 판

- 판 ID, 앞 판(보통 하나, 합칠 때 둘), 쓴 기기, 시각(HLC), 남길 말, 그 판의 제목, 본문(나무마크 · zstd).
- 같은 앞 판에서 두 판이 갈라지면 충돌이다(6-4).
- 지우기는 표시 판이다. 판 기록은 남는다.

### 5-3. 분류 나무 — 첫 분류가 집

- 문서의 첫 `[[분류:…]]`가 나무 속 자리. 나머지 분류는 문서 위 글줄로만 보인다.
- 분류의 부모 = **분류 문서의 첫 분류**(「분류:조선 선조」 → 「분류:조선」).
- 분류 문서가 없는 분류는 맨 위에 「상위 분류 없음」 표시로 선다. 고리는 끊고 경고한다.
- 폴더의 수 = 그 아래 문서의 합(색인이 세어 둔다). 분류가 없는 문서는 「분류 안 됨」.

### 5-4. 첨부

- 그림 · PDF는 내용 해시(SHA-256)를 이름으로 둔다. `파일:` 문서가 이름 · 출처 · 저작권 · 해시를 가진다. 폰은 열 때 받는다.

### 5-5. 색인(언제든 다시 지을 수 있는 파생물)

| 색인 | 쓰는 곳 |
| --- | --- |
| 검색(제목 · 본문) — 한글 · 한자 2글자 조각, Rust FTS5 토크나이저 | 찾기 · 창구 `search` |
| 링크(있는 문서 · 만들 문서) | 보기 · 만들 문서 · 많이 불리는 문서 · 갈래를 잇는 링크 |
| 분류 나무와 폴더별 수 | 사이드바 · 주제 바로가기 |
| 각주와 사료(각주 속 『…』) | 많이 인용한 사료 · (나중) 출처 보강 |
| 연표 연결(항목ID ↔ 문서) | 창구 `docs_for_entity` · 다루는 해 |
| 틀을 쓰는 곳 | 틀이 바뀌면 그 틀을 쓰는 문서만 다시 그림 |
| 통계 모음(갈래 사이 링크 수 · 달마다 새 문서 · 날마다 고친 횟수) | 서재 통계 · 쓰는 리듬 |
| 다루는 해 — ① 이어진 연표 항목의 기간 → ② 정보 상자 틀의 `기간` · `연도` → ③ 해 없음 | 서재가 다루는 시대 |

색인은 문서마다 "어느 판까지 했는지"를 들고, 낡은 문서만 뒤에서 고친다. **시작할 때 통째로 다시 짓지 않는다.**

### 5-6. 그리기 모델

- 저장할 때 엔진이 나무마크를 한 번 해석해 블록 목록으로 굳힌다: 제목 · 문단(글 · 링크 · 각주 표 · 한자 구간 · 루비) · 표 · 목록 · 펼친 틀 · 매크로 자리(목차 · 연표 띠 · 대문 덩어리) · 그림.
- 아카이브와 HistoryTime의 `library_view`는 이 모델만 그린다. 나무마크 해석기는 Rust 한 벌.
- 링크가 있는 문서인지는 모델에 굳히지 않는다. 볼 때 `titles_exist`로 한 번에 묻는다(새 문서가 생겨도 다른 문서의 모델을 다시 짓지 않는다).

### 5-7. 파일 배치(기기마다)

`library.db`(원본: 문서 · 판 · 첨부 정보 · 동기화 상태) · `index.db`(파생: 검색 · 링크 · 나무 · 그리기 모델 · 통계 — 지워도 다시 짓는다) · `blobs/`(첨부) · `local.db`(기기 상태).

### 5-8. 나무마크

지금 Dart 해석기(`packages/core_engine/lib/src/wiki/`)가 받는 문법 — 링크 · 각주 · 분류 · 표 · 틀 `include` · 루비 · `[목차]` · 매크로 — 을 `spec/namumark.md`로 못박고, 지금 해석기의 검사를 정답지로 Rust에 옮긴다. 대문 매크로(`[오늘의 역사]` 등, 8-2)와 연표 문법(7-1)을 더한다.

## 6. 동기화

### 6-1. 운반

- 구글 로그인 · 드라이브 통신은 **아카이브 앱만** 한다. 묶음을 만들고 적용하는 일은 엔진이 하고(`spec/drive-format.md`), 앱은 올리고 받기만 한다. 엔진은 네트워크를 모른다.
- 드라이브에는 **보이는 폴더**(가칭 「역사 서재」). 권한은 `drive.file` 하나.
- 개인용 구글 클라우드 프로젝트와 OAuth 클라이언트를 한 번 등록한다. 비밀값은 저장소에 넣지 않는다.

### 6-2. 드라이브 속 모양

```
역사 서재/
  library.json                 서재 ID · 형식 판
  devices/<기기ID>.json         기기 이름 · 마지막으로 올린 묶음 번호
  log/<기기ID>/<번호>.pack      바뀐 내역 묶음(zstd) — 기기마다 자기 폴더에만 쓴다
  snapshot/<번호>.tar.zst       통째 사본 + 기기별로 어느 묶음까지 담았는지
  blobs/ab/<해시>               첨부
```

- 기기마다 자기 폴더에만 쓰므로 같은 파일을 두 기기가 덮어쓰지 않는다.
- 묶음 속 항목(판 더하기 · 문서 만들기 · 이름 바꾸기 · 지우기 · 첨부 더하기)은 모두 ID가 있어 두 번 받아도 한 번만 든다.

### 6-3. 언제

- 올리기: 저장하고 몇 초 뒤(모아서) · 앱을 닫을 때.
- 받기: 켤 때 · 다시 앞으로 올 때 · 켜져 있는 동안 몇 분마다(드라이브 변경 목록 API).
- 오프라인: 모든 일은 로컬에서, 올릴 묶음은 쌓아 둔다.

### 6-4. 겹침

- 겹치지 않게 고쳤으면 공통 조상 판으로 3-방향 **자동 합치기**. 합친 판의 ID와 내용은 두 앞 판에서 **결정적으로** 만든다(폰과 PC가 저마다 합쳐도 같은 판).
- 같은 곳을 다르게 고쳤으면 **충돌**: 늦게 고친 판을 보이고 「다른 기기에서 고친 판과 겹침」 띠를 띄운다. 편집 화면에서 나란히 견주어 합치면 앞 판이 둘인 판이 생긴다. 두 판 모두 판 기록에 남는다.
- 고친 것과 지운 것이 겹치면 고친 쪽이 이기고 알린다.
- 같은 제목의 새 문서가 두 기기에서 따로 생기면 둘 다 남고 「같은 제목 문서 둘」로 알린다. 그동안 링크는 먼저 만든 쪽으로.

### 6-5. 새 기기 · 큰 서재

- 새 기기는 가장 최근 통째 사본을 받고 그 뒤 묶음만 적용한다.
- 통째 사본은 와이파이 · 전원이 있는 PC가 가끔(예: 묶음 5,000개마다) 올린다. 그보다 오래된 묶음은 사본이 둘 이상 생긴 뒤에야 지운다.
- 첨부: 폰은 열 때 받는다. 「와이파이에서 모두 받기」를 고를 수 있다.

### 6-6. 보내지 않는 것 · 백업

- 자전 · 연표 자료집 · `local.db`는 보내지 않는다. 쓰는 리듬 · 통계는 판에서 다시 센다.
- 드라이브 동기화는 백업이 아니다(지운 것도 옮긴다). 대신 지우기는 표시만 하고 판을 남기며, 설정에 ZIP 내보내기를 둔다.

## 7. 앱 사이 잇기

### 7-1. 연표 문법(아카이브가 쓴다)

- `[[연표:<항목ID>|보이는 글]]` — 연표 항목 링크. 누르면 HistoryTime이 그 항목에서 열린다.
- `[연표(<항목ID>, 범위=1592..1598)]` — 문서 속 연표 띠. 사건은 볼 때 연표 창구 `strip`에서 받는다. HistoryTime이 없으면 "제목 · 범위"만 적힌 자리로 보인다.
- 항목ID = HistoryTime 형식 4의 바뀌지 않는 ID. 편집기에서 `[[연표:`를 치면 연표 창구 `search_entities`로 이름을 찾아 넣는다.

### 7-2. 딥링크

- `historyarchive://doc/<문서ID>` · `/edit/<문서ID>` · `/new?title=…&draft=<파일>` · `/kangxi/<글자>`
- `historytime://entity/<항목ID>` · `historytime://date/<월-일>`
- Android는 intent filter, Windows는 설치할 때 HKCU에 프로토콜 등록(이미 켜져 있으면 한 개만 실행하는 장치로 첫 창에 넘김). 받을 앱이 없으면 안내.

### 7-3. 같은 기기 창구(읽기 전용, 양방향)

아카이브의 **서재 창구**: `doc(문서ID)` · `doc_by_title(이름공간, 제목)` · `docs_for_entity(항목ID)` · `titles_exist([…])` · `search(검색어)` · `hanja(글자)`(HistoryTime 문서 속 한자에도 같은 자전 카드).

HistoryTime의 **연표 창구**: `entity(항목ID)` · `entities_on_date(월, 일)`(대문 오늘의 역사) · `search_entities(검색어)` · `strip(항목ID, 범위)` · `spans(항목ID들)` + `data_version`(다루는 해 — 자료 판이 바뀔 때만 다시 받음).

- Windows: 각 앱이 HistoryCore 엔진을 읽기 전용으로 열어 상대 저장소 파일을 직접 읽는다(SQLite WAL). 위치는 정해진 경로 + 레지스트리 열쇠.
- Android: 각 앱이 ContentProvider를 열고 **서명 수준 권한**으로 막는다. 그래서 **아카이브와 HistoryTime APK는 같은 서명 키로 서명한다.**
- 창구마다 `api_version`. 판이 맞지 않으면 그 기능만 조용히 빠진다.

### 7-4. HistoryTime 자료집 속 문서

- DLC 자료집의 문서(원문)는 연표의 참고 자료다. 서재에 들이지 않고 HistoryTime이 보여 준다.
- 고치거나 덧붙이려면 아카이브의 **「서재로 가져오기」**: 원문을 나무마크로 바꾸고, 그 항목으로의 연표 링크와 출처(자료집 · 원본 열쇠 · 판)를 붙인 서재 문서를 새로 만든다. 자료집 원문이 바뀌면 그 문서에 「자료집 원문이 바뀜 — 견주기」를 띄운다.
- 옛 모듈 방식의 `module_document` 충돌 표는 이 장치 하나로 바뀐다.

### 7-5. 히스토리챗(다음 판)

- 쓰기는 「아카이브로 보내기」: Windows는 초안 파일 + `historyarchive://new?draft=…`, Android는 공유 intent. 아카이브는 초안을 편집 화면에 열기만 하고 저장은 사용자가 한다.
- 읽기는 HistoryCore 엔진의 WASM 판으로 나중에 붙인다.

## 9. 단계와 검증

원칙: HistoryTime 엔진처럼 **잰 수치로 통과를 정한다.** 측정 판을 엔진보다 먼저 만든다.

### 9-1. 단계

| 단계 | 하는 일 | 끝의 모습(통과 기준) |
| --- | --- | --- |
| P0 바탕 | HistoryCore(Rust 작업공간 · Flutter 패키지 · `spec/`)와 새 아카이브 저장소. 글꼴 · 심벌 · 康熙字典 자료 · CI 틀을 옮김 | 빈 앱이 Android · Windows에서 Rust 엔진을 불러 엔진 판 번호를 띄움(CI 통과) |
| P1 측정 판 | 100만 건 더미 서재 도구(실제 같은 나무마크 · 분류 나무 · 링크 · 각주 · 한자) + PC · 폰 측정기 | 측정기가 돌고 9-2와 견줄 기준 수치가 나옴 |
| P2 서재 엔진 | 저장 · 판 · Rust 나무마크 해석기 · 그리기 모델 · 5-5의 색인 여덟 · 증분 색인 · 자전 질의 | **100만 건에서 9-2 통과**(PC 필수, 폰은 수치 보고) |
| P3 아카이브 화면 | 셸과 다섯 화면, 대문 매크로, 편집기 | 화면마다 taste-skill 검사기 1440 · 768 · 390 통과 + 목업과 견준 스크린숏 |
| P4 동기화 | 드라이브 형식 · 묶음과 통째 사본 · 운반 · 자동 합치기와 충돌 | 기기 둘 · 셋 흉내 무작위 시험에서 늘 같은 서재로 모임 · 끊긴 올리기에도 안전 · 실제 계정 시험 |
| P5 창구와 딥링크 | Windows 읽기 전용 열기와 레지스트리 · Android ContentProvider(서명 권한) · `api_version` | 시험용 작은 앱이 두 플랫폼에서 문서와 자전 카드를 읽어 옴 |
| P6 첫 릴리스 | 설치 EXE · 포터블 ZIP · APK · 서명 · 연기 시험 | **아카이브 0.0.1** |

- P2와 P3는 엔진 질의 API가 정해진 뒤 나란히 한다.
- 판 번호는 0.0.1로 새로 시작한다. 같은 앱 이름 · 설치 정보(Windows `AppId`, Android 패키지 이름)를 써서 옛 앱 위에 덮어 설치되게 하고, Android `versionCode`만 13부터 잇는다.

### 9-2. 100만 건 예산표

| 일 | 예산 |
| --- | --- |
| 제목 찾기 | p99 ≤ 10ms(옛 설계서 7장) |
| 본문 찾기 첫 20건 | p95 ≤ 10ms(옛 설계서 7장) |

### 9-3. 검사

- Rust: 단위 검사, 나무마크 정답지(지금 Dart 검사 + 나무위키식 견본), 해석기 퍼징, **동기화 수렴 성질 검사**(무작위 편집을 기기 여럿에 흩고 받는 차례를 섞어도 결과가 바이트까지 같음), **실패 주입**(색인 · 적용 도중 끊어도 저장소 온전).
- Flutter: 위젯 검사, 스크린숏, taste-skill 검사기.
- CI: Android · Windows 빌드, 설치와 실행 연기 시험.
