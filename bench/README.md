## P2-3 검색 조각 측정 (2026-10-22)

`hc-bench search --docs <수> --dir <폴더>` — 본문 plain 글을 한글 · 한자 2글자 조각으로 잘라 contentless FTS5(`detail=none`)에 넣고, 3글자 넘는 검색어는 조각 AND로 후보를 얻어 저장한 plain(NFC)으로 확인한다. 일감은 위와 같은 본문 질의 1,000개.

| | 10만(첫 판) | 10만 | 100만 |
| --- | --- | --- | --- |
| 짓기 | 93.3초 | 35.3초 | 1,361초 |
| optimize | 14.9초 | 4.0초 | 58.8초 |
| 파일 크기(조각 색인 + plain) | 0.31GB | 0.31GB | 3.10GB |
| 본문 찾기 첫 20건 p50 · p95 · p99 · 최대 | 0.35 · 65.19 · 237.49 · 1,074.69ms | 0.19 · 4.20 · 19.21 · 139.12ms | 0.15 · **4.07** · 23.13 · 255.22ms |
| 질의당 확인한 후보 | 14.4 | 14.4 | 12.7 |

- 첫 판이 느렸던 까닭은 FTS가 아니라 확인이었다(조각 AND 자체는 1ms 안). 후보마다 읽기 0.11 + 풀기 0.16 + 정규화 0.37ms가 들고, 조각은 맞지만 낱말이 아닌 후보가 수백~천여 개인 검색어(「밝음이며」 1,152개)가 꼬리를 만들었다.
- 고친 것:
  - plain은 저장할 때 NFC로 맞추고 찾을 때는 그대로 견준다(확인 덩이는 한글 · 한자뿐이라 대소문자가 없다).
  - 풀기 문맥을 다시 쓴다.
  - 짓는 동안 FTS5 `hashsize` 256MB · `automerge` 0, 끝에 `optimize` 한 번.
- 100만 짓기 1,361초는 같은 PC에서 다른 세션의 Rust 빌드와 겹친 값이다(20만 편 구간이 91–509초로 흔들림). 조용했던 구간(80만→100만, 20만 편 91초)으로 보면 쓰는 쪽 하나의 FTS 짓기는 100만에 약 8분이다.
  - 그래서 통째 짓기는 FTS를 넷(`rowid % 4`)으로 나눠 나란히 짓는다(P2-3 Task 7).

## 이 수치를 읽을 때

- **기준 구현의 조건**: 색인은 (ns, title) · (ns, updated) · (ns, grp) · 분류 소속 · FTS5 trigram. 2글자 이하 검색은 trigram이 못 찾아 `LIKE`로 훑는다. 저장은 본문 · FTS만 고치고 판(이력) · 분류 소속은 고치지 않는다. `synchronous=NORMAL`, 캐시가 데워진 상태에서 잰다.
- **한 번 잰 값이다.** 같은 10만을 두 번 재니 저장 한 편 p95가 203ms · 31ms, 대문 모음이 51ms · 13ms로 흔들렸다(앞의 것은 직전에 지운 11GB 작업 파일의 디스크 정리와 겹친 것으로 본다). 엔진과 견줄 때는 같은 기계에서 연달아, 가능하면 여러 번 잰다.
- **백분위가 없는 예산 줄**(분류 폴더 · 대문 · 시작)은 p95로 판정한다.
- **아직 재지 않는 것**: 바뀐 내역 묶음 적용(P4). 저장 공간은 합계만 낸다 — 원본 · 색인 · 검색 비율 나누기는 남았다.
- 앞선 기록: 처음 잰 기준 서재는 대문 모음용 색인이 없어 100만에서 대문 모음이 초 단위로 나왔다. 그 수치는 SQLite의 바닥이 아니라 빠진 색인을 잰 것이라 버리고 다시 쟀다.
